1Problem statement

HR adds and removes staff's access to company tools by hand. For each joiner, HR asks IT to create accounts and licences one tool at a time, and tracks the replies in chats and sheets. For each leaver, the same work has to be done in reverse, and it is easy to miss one.

This causes three problems:

  • Slow onboarding. A new joiner can wait days before they have working access.
  • Risky offboarding. A tool left active after someone has left is a security exposure. Paid seats (Claude, GitHub, Google Cloud roles) are also wasted.
  • No record. There is no single view of who had access to what, when it was granted, and when it was removed. Audits take hours of manual checking.
Goal: HR enters a joiner's details once and their access is set up in one flow. HR removes a leaver's access in one confirmed action. Every change is recorded.

Measure of success: a joiner has all default tools on day one with no IT tickets; a leaver has no active tool access by the end of their last working day; an access report can be produced in minutes.

2End-to-end workflow

The workflow has two main paths: onboarding and offboarding. Both use the same steps for each tool, and both finish with a checklist and an audit record.

2.1 Onboarding

  1. HR creates the employee recordName, personal and work email, department, manager, start date and job title are entered once. The work email is generated from the company naming format.
  2. The system selects the access bundleEach department has a default set of tools. HR can add or remove tools for this person before continuing.
  3. HR confirms and starts provisioningNothing is created until HR clicks the confirm button. The confirmation lists each tool that will be granted.
  4. Each tool is granted, one at a timeGoogle Workspace account first, then Gemini licence, Claude seat, GitHub membership and Google Cloud roles. Each result is saved immediately.
  5. Failures are retried or flaggedA temporary error is retried automatically. A permanent error (for example, no seats left) is shown under "Needs attention" with a Retry button.
  6. Manual checklist is completedItems the systems cannot do, such as laptop issued, ID card issued, policy documents signed and welcome call, are ticked by IT or HR.
  7. Onboarding closesWhen every automatic grant and every checklist item is done, the status becomes Active and the audit log records the completion.

2.2 Offboarding

  1. HR selects the leaver and last working dayHR also chooses who receives the leaver's Drive files and email.
  2. The system shows exactly what will be removedA list of every active tool, with the action for each. HR confirms with one click. The leaver can be offboarded now or scheduled for the last working day.
  3. Google account is suspended firstThis blocks sign-in to every tool that uses Google login, which is the fastest way to cut access.
  4. Other tools are removedGemini licence, Claude seat, GitHub membership and Google Cloud roles are removed. Each step is recorded; failures are retried or flagged.
  5. Files are transferredDrive files and email are moved to the nominated person, as set in step 1.
  6. Return items are collectedLaptop, ID card and final settlement are ticked off as completed.
  7. Offboarding closesStatus becomes Offboarded, and an access report is available for records.

2.3 Audit and reporting

Every action, whether by a person or by the system, writes one audit entry: who did it, what changed, the time, the tool and the result. Entries cannot be edited or deleted. A report can be filtered by person, tool, date or result and exported.

3Technical architecture

The system has four layers. Each layer has one job, and only the backend layer talks to the database and to company systems.

3.2 Data model (main tables)

TableHolds
employeesPerson details, department, manager, dates, status (onboarding, active, offboarding, offboarded).
access_templatesDefault tool set for each department.
applicationsThe tools, and the connector each one uses.
access_grantsOne row per person per tool: requested, active, failed, revoked; plus external ID and error.
checklist_itemsManual onboarding and offboarding tasks, with owner and completion.
jobsQueue of tool calls to run, with attempts and last error, for retries.
audit_logAppend-only record of every action; each row stores a hash of the previous row, so edits are detectable.
hr_usersWho may use the system, and their role: HR admin, HR viewer or IT.

3.3 Security and controls

  • Access to the system: only people listed in hr_users can call any backend tool. Destructive actions (offboarding, removing access) need the HR admin role.
  • Secrets: admin keys and service-account credentials are kept in Secret Manager, never in code or on the page. Google access uses domain-wide delegation with only the scopes required.
  • Least privilege for the database: the backend role can insert and read the audit log, but cannot update or delete rows in it.
  • Personal data: personal email is encrypted at rest; only the fields needed for the workflow are collected.
  • Safe retries: each grant or removal is idempotent, so running it twice does not create a second account or fail on the second run.
  • Deployment: database migrations run before the backend is deployed; production changes need a second reviewer.

3.4 Delivery pipeline

  1. BuildCode and schema changes are reviewed in a pull request, then merged.
  2. TestUnit tests for each connector with mocked APIs; tests that onboarding twice gives one account.
  3. StagingDeploy to a staging service with a test database and a test Google organisational unit. Run a dummy joiner and leaver end to end.
  4. ProductionMigrate the database, then deploy the backend. The page is republished only when its own files change.
  5. MonitorAlerts for failed jobs and connector errors go to IT and HR; logs are retained for audit.

4Normal architecture (plain-language view)

This section explains the same system without technical terms, for readers who need to know what it does, who uses it, and where information goes.

4.1 What happens in plain words

  • When someone joins, HR fills in one form. The system switches on the tools for their team, and HR sees a list of what is done and what needs attention.
  • When someone leaves, HR picks the person and the date, reviews the list of tools to be removed, and confirms once. The system cuts Google access first, then removes the rest.
  • When something fails, the system tries again. If it still fails, HR sees the problem on the home screen with a button to retry.
  • At any time, HR can see who has which tool, and a full history of changes with the date and who made each one.

4.2 What the system does not do

  • It does not replace payroll, the HR records system, or recruitment in this phase.
  • It does not manage laptops or desk items; it only tracks them on the checklist.
  • It does not change any tool until HR confirms the action.

5Test cases

Tests run at four levels. Unit tests check each rule and connector in isolation. Integration tests check the backend against a real PostgreSQL database with mocked company APIs. End-to-end tests run the full joiner and leaver flows in staging. User acceptance tests are run by HR on the staging page before go-live.

Test data only. Every test uses dummy employees and the staging Google organisational unit. No test touches a live account or a real licence.

5.5 Exit criteria

  • All unit, integration and security tests pass in the delivery pipeline before staging deploy.
  • ON-01, OFF-01 and SEC-01 to SEC-06 pass in staging with a dummy joiner and leaver.
  • HR completes the UAT cases on staging and signs off.
  • No open defect that can grant or remove access incorrectly.
