HR backend: how it works and how we deploy it

Draft for the two-person team · 13 October 2026 · Describes what is built today and what is planned. Items marked "planned" do not exist yet.

1The short version

The backend is one TypeScript service. HR uses a page inside Claude; the page sends each action to the service; the service checks who is asking, does the work in PostgreSQL and in the company tools, and writes an audit entry for every step.

Today it runs on one laptop with a local database and stand-in connectors. To go live we put the service on Google Cloud Run, the database on Cloud SQL, keep keys in Secret Manager, and ship changes through an automatic test-then-deploy pipeline.

Built today: database schema, 46 employees loaded, 8 tools, audit hash chain, 7 passing tests, stand-in connectors. Planned: real connectors, scheduled offboarding, HTTP hosting, cloud deployment, pipeline, monitoring.

2How a request runs

This is what happens when HR clicks a button, for example "Offboard".

  1. HR acts in the pageThe page holds no keys. It only names the tool and the inputs.
  2. The connector forwards the callThe call carries the signed-in user's identity. The page cannot call anything that was not declared when it was published.
  3. The backend checks the roleThe user must be in hr_users. Admin can change access; viewer can only read.
  4. The workflow runsRules decide the order (Google first when removing). Each tool is called one at a time.
  5. Results are savedEach tool's result is written to access_grants as soon as it comes back.
  6. The audit entry is writtenSame transaction. Each entry stores a hash of the one before it.
  7. The result returnsSuccess, or a plain error message, comes back to the page.

Scheduled offboarding (planned)

Chintan Limbad's last working day is 31 October, so this comes first. A daily job runs at a fixed hour, finds employees whose last working day is today and whose status is still active, and starts the same offboarding steps as a named system user. The job is triggered by Cloud Scheduler and runs as a Cloud Run Job, so it needs no always-on server.

Failures and retries (planned)

A temporary failure is retried automatically, up to three times. After that the tool is flagged under Needs attention, and HR can press Retry. Each retry is logged. Running a step twice is safe: a tool that is already active is not granted again.

6Where it runs: deployment architecture

PartWhy this choice
Cloud RunRuns our container over HTTPS with no servers to manage. It scales down when nobody is using it, which suits an HR tool used a few times a day.
Cloud SQL (PostgreSQL)Same engine we already use locally, with automatic backups and point-in-time recovery. Reached over a private connection, not the public internet.
Secret ManagerKeys are read at start-up and never stored in the code or the image.
Cloud Scheduler plus a Cloud Run JobStarts the daily offboarding check without an always-on process.
Artifact RegistryStores each built image, so staging and production run the exact same one.
Logging and alertsTells IT when a job fails or a connector keeps erroring.

Changes needed in the code before it can run on Cloud Run

  • Switch from local to HTTP. Today the server talks over a local pipe (for the desktop app). Cloud Run needs it to listen on a web port and speak the remote MCP protocol.
  • Real sign-in. Today the caller is set by an environment variable. In the cloud, the caller must come from a verified sign-in, restricted to the company's Google domain. How the claude.ai connector signs users in must be confirmed with your claude.ai admin when the connector is registered.
  • Read settings from the environment. Database address and secrets come from Cloud SQL and Secret Manager, not defaults in the code.
  • Add a health check. A small endpoint Cloud Run uses to know the service is up.

8How changes ship: the pipeline

1 PushChange goes to Git on a branch
▸
2 TestUnit and database tests run automatically
▸
3 ReviewSecond person approves the pull request
▸
4 BuildContainer image built and stored
▸
5 StagingMigrate database, deploy, run checks
▸
6 ApprovePerson signs off the staging run
▸
7 ProductionSame image, migrate, deploy, watch
  • Tests block the pipeline. If any test fails, nothing is built or deployed.
  • Migrations run first and only add. New columns and tables go in before the new code needs them, so the old version keeps working if we roll back.
  • Same image, two places. What passed on staging is exactly what runs on production.
  • Rollback. Cloud Run keeps earlier versions; sending traffic back to the last good one takes one command and does not touch the database.

11Go-live checklist

  • All automated tests pass and the pipeline is green.
  • A dummy joiner and a dummy leaver complete on staging, with a full audit trail.
  • Real connectors tested on staging for all five tools.
  • Scheduled offboarding tested with a dated dummy leaver.
  • Production secrets set; staging secrets cannot reach production.
  • HR users and roles reviewed by the manager.
  • Backups restored once on staging to prove they work.
  • Rollback rehearsed.
  • HR has signed off the staging run.
